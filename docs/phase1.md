# フェーズ1仕様書：データ保存と再接続機能

## 【目標】
通信切断時にプレイヤーデータが消える問題を解決し、アプリが落ちても日常の延長のようにスムーズにゲームへ復帰（再接続）できる土台を作ります。

## 【実装タスク】

### 1. データベース（モデル）の更新
`models` フォルダ内のプレイヤー用の構造体（例：`Player`）に、以下のフィールドが揃っているか確認し、不足していれば追加してください。GORMの `AutoMigrate` でSQLiteのテーブルが正しく更新されるようにします。

- `ID`: 主キー
- `RoomID`: 部屋のID（4桁の文字列）
- `UserID`: フロントエンドから送られてくるユーザー固有のID
- `Name`: プレイヤーの名前
- `Role`: 役割（0: 逃走者, 1: 鬼）
- `IsCaught`: 捕まったかどうかのフラグ（true / false）
- `Lat`, `Lng`: 緯度と経度
- `Color`: メンバーカラー（文字列。※フェーズ3の先取り要件です）

### 2. 入室（Join）処理の改修：再接続ロジックの追加
WebSocketで `action: "join"` を受け取った際の処理を以下のように書き換えてください。

- フロントから送られてきた `user_id` と `room_id` を使って、データベース（`players` テーブル）を検索します。
- **【新規の入室場合】**
  - DBにデータがなければ、新しいプレイヤーとしてDBに保存（Insert）し、サーバーのメモリ（Hub等）にも接続を登録します。
- **【再接続（復帰）の場合】**
  - すでにDBに同じ `user_id` のデータがある場合、DBから過去の状態（役割 `Role` や生存状態 `IsCaught` など）を読み込みます。
  - 読み込んだ状態をサーバーのメモリ（Hub等）に復元し、プレイヤーをゲームに復帰させます。

### 3. 状態変化時のDB保存（Update）の徹底
ゲーム中にプレイヤーの状態が変わった際、メモリ上のデータ更新だけでなく、**必ずDB（`players` テーブル）も更新（Update）**してください。
- 更新するタイミング：
  - ゲーム開始時（全員に役割 `Role` が割り振られた瞬間）
  - 確保成立時（逃走者の `IsCaught` が true に変わった瞬間）

### 4. 切断（Disconnect）処理の変更
プレイヤーのWebSocket通信が切れた際、サーバーのメモリ（現在の接続一覧）からは削除しますが、**DB（`players` テーブル）のレコードは絶対に削除（Delete）しないでください**（削除すると再接続できなくなります）。
