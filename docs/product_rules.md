# プロダクトルール

この資料は、鬼ごっこアプリとして守るゲーム上のルールと状態遷移をまとめたものです。

## 基本ルール

- プレイヤーはルームに入室してゲームに参加します。
- ゲーム開始時に各プレイヤーへ役割が割り当てられます。
- 役割は `0` が逃走者、`1` が鬼です。
- 鬼は逃走者に対して確保確認を送り、逃走者が承認すると確保成立になります。
- 逃走者が全員捕まる、または制限時間が終わるとゲーム終了です。

## ルーム状態

`Room.Status` は以下の値で管理します。

| 値 | 状態 | 意味 |
| --- | --- | --- |
| `0` | 待機中 | 入室と設定変更を行う段階 |
| `1` | 進行中 | ゲーム開始後から結果発表前まで |
| `2` | 終了 | ゲームが終了した状態 |

フロント側では、待機画面、ゲーム画面、結果画面の切り替えをこの状態に合わせて設計します。

## ゲーム開始

ゲーム開始時の流れは以下です。

1. フロントから WebSocket で `action: "start"` と `oni_users` を送信します。
2. サーバーが `oni_users` に含まれる参加中プレイヤーを鬼、その他を逃走者にします。
3. 各プレイヤーへ `event: "start"` が届きます。
4. `grace_period` が終わると `event: "game_active"` が届きます。
5. 本編中は `sync_interval` ごとに `event: "sync"` が届きます。

鬼に指定されたプレイヤーの色は、ゲーム開始時にサーバー側で `black` に上書きされます。

`start` と `game_active` は役割が違います。`start` はゲーム開始操作を受け付けた通知で、`game_active` は猶予時間後に本編を開始する通知です。

## 猶予時間

`grace_period` は秒単位です。

- 逃走者が逃げるための猶予時間として扱います。
- 猶予時間中もプレイヤーの位置情報更新は送信できます。
- 確保操作や本編用 UI は `game_active` 後に有効化する想定です。

## 位置同期

位置情報は `move` と `sync` で扱います。

- フロントは自分の位置を `move` で送信します。
- サーバーは受け取った位置を DB とメモリに保存します。
- サーバーは `sync_interval` ごとに全員の位置を `sync` で配信します。

`move` のたびに全員へ配信する設計ではないため、フロントの地図表示は `sync` を基準に更新してください。

## 確保フロー

確保は確認制です。

1. 鬼が対象の逃走者に対して `capture_request` を送ります。
2. 対象の逃走者だけに `capture_checking` が届きます。
3. 逃走者が `capture_response` を返します。
4. 承認された場合は `captured` が全員に届きます。
5. 拒否された場合は `capture_denied` が全員に届きます。

確保が成立すると、対象プレイヤーの `is_caught` は `true` になります。

## 終了条件

ゲームは以下のどちらかで終了します。

- 制限時間が終了した
- 逃走者が存在し、かつ逃走者全員の `is_caught` が `true` になった

終了時は `result` が配信されます。全員捕獲で終了した場合は、最後の `captured` の直後に `result` が配信されます。`result.survivors` には最後まで捕まらなかった逃走者の `user_id`、`result.results` には鬼を含む各プレイヤーの最終状態が入ります。

## 再接続

WebSocket が切断されても、プレイヤー情報は DB に残ります。

同じ `room_id` と `user_id` で `join` し直すと、保存済みの名前、役割、確保状態、位置、色をもとに復帰します。フロント側では `user_id` をリロード後も維持してください。
